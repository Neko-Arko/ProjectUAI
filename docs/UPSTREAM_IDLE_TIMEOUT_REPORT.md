# Upstream idle timeout investigation

Reviewed October 25, 2026 against Project UAI 3.7.1.

Reported error: `Provider stream failed: Upstream idle timeout exceeded`.

## Finding

The available evidence points to an error reported by the upstream provider or
its gateway. UAI Bridge adds `Provider stream failed:` when it receives a failure
inside an event stream. The remaining message comes from that upstream event;
`Upstream idle timeout exceeded` is not a timeout message generated by this
repository.

An idle timeout generally means the service stopped receiving expected stream
activity from its own upstream for too long. A slow model, heavy load, a long
initial processing period, or a stalled connection could explain that silence.
Those are possibilities, not a diagnosis of this particular request.

## Evidence

- [Bridge stream handling](../bridge/inference.js#L313) extracts the upstream
  error's message, reason or code, redacts credentials, and adds the prefix.
  It recognizes SSE errors and failed/incomplete response events.
- [Bridge inference setup](../bridge/inference.js#L281) deliberately ignores
  legacy elapsed-time limits. It also removes `x-stainless-timeout` from outgoing
  headers and [disables the Node request socket timeout](../bridge/inference.js#L421).
- The [Android relay](../companion/app/src/main/kotlin/dev/projectuai/relay/engine/JobEngine.kt#L371)
  likewise has no fixed provider read timeout.
- The existing [stream failure fixture](../bridge/tests/streaming.test.js#L211)
  covers failure after partial output and later completion markers. UAI retains
  failure rather than treating a partial response as complete.

## Practical implications

Increasing UAI's request timeout does not change the provider gateway's own idle
threshold. Adding or rotating API keys is also not a demonstrated solution to
this error: it reports stream inactivity, not an invalid key or quota refusal.

A manual retry can establish whether the incident was transient. If it repeats,
comparing the same request with another model or provider can help identify
whether it follows one route. A shorter context can be a useful controlled
comparison when the delay occurs before any output, but is not a confirmed fix.

UAI does not automatically replay a failed partial stream, because the remote
request may already have produced output or performed work.

## Limits

No matching failing request log was available in the inspected workspace. The
error alone does not identify the provider, model, configured idle threshold,
elapsed time, or whether output had already arrived. The failing log's endpoint,
model, timing and redacted error frame would be needed to narrow those down.
No timeout or retry behavior was changed for this investigation.
